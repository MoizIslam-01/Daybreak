# Daybreak

> A mobile, asynchronous, team-based auto-battler built in Unity. You set your orders once a day;
> every night the server resolves every battle automatically. You wake up to the results.

Daybreak is built for a friend group after graduation. The design goal isn't engagement metrics —
it's *"is there something worth arguing about in the group chat tomorrow morning?"* Every mechanic
below is chosen to serve that.

**Status:** Milestone 0 of 6 complete — the foundations are in and verified end to end.

---

## The idea

Everyone spends about two minutes a day building a squad and picking a strategy, then locks it in.
Overnight, every player's squad fights every other player's squad. In the morning you watch the
replays, see where you landed on the weekly leaderboard, and talk trash.

- **Two minutes a day, and forgiving.** Miss a day and your last squad auto-repeats. The flakiest
  friend still participates.
- **Strategic, not twitchy.** Depth comes from reading the meta and countering it. Every input is a tap.
- **Everyone starts equal, every week.** No power progression, no grind advantage. Rewards are purely
  cosmetic, and the currency rewards *showing up* over winning. The power gap between the sweatiest
  and the flakiest player is always exactly zero.
- **The daily resolve is a shared moment.** Results drop for everyone at the same time.

## How a battle works

A squad is **5 units on a 2×3 grid** — front row soaks damage, back row deals it — plus **one
tactic** for the whole team.

Every unit is one of three archetypes forming a counter triangle:

```
Vanguard ──beats──► Skirmisher ──beats──► Marksman ──beats──► Vanguard
```

Favorable matchups deal ×1.25 damage, unfavorable ×0.80. Vanguards are tanky melee front-liners,
Skirmishers are fast melee attackers, Marksmen are ranged glass cannons that dive the enemy back row.

Units also carry a **synergy tag** (Guardian, Pack, Arcane, Swift). Fielding two or three of a tag
buffs the whole team, and tags cut *across* archetypes — so committing to a synergy costs you
flexibility in the counter game. That tension is the core decision.

**Tactics** reshape targeting: `Balanced`, `Focus Fire` (pile onto the lowest-HP enemy),
`Protect Backline` (clear the enemy front row first), or `Berserk` (+25% ATK, −25% DEF, target the
biggest threat).

Battles are round-based, capped at 30 rounds, and resolved with **integer math only**.

## Architecture

The one non-negotiable design rule:

> **The battle simulation is a pure C# library with no `UnityEngine` dependency.**

`Daybreak.Sim` is enforced Unity-free by an assembly definition, which lets the *identical source*
compile in two places: the Unity client (for local practice and preview battles) and a
**Unity Cloud Code C# module** on the server, which is the authoritative resolver. Cloud Code runs on
the open-source .NET runtime and cannot reference `UnityEngine` — hence the boundary.

```
Assets/Daybreak/
  Sim/         Daybreak.Sim     — deterministic battle sim, no Unity reference
  Client/      Daybreak.Client  — UI, services, replay renderer
  Resources/   units.json       — the shared unit table, read by client AND server
  Tests/       EditMode tests, including the boundary guard
CloudCode/     The server module — compiles the same Sim source, embeds the same units.json
```

A unit test asserts that `Daybreak.Sim` references no Unity assembly. If it ever goes red, the
server can no longer resolve battles — it's treated as a build blocker, not a warning.

### Determinism

Because the server runs the sim once and the outcome is reproducible, **a stored replay is just
`(squadA, squadB, weeklyModifier, seed)`** — a few hundred bytes, not a video. The full event log is
regenerated by re-running the sim whenever someone taps "watch." The client animates that log and
owns no game logic whatsoever.

That only works if the sim is rigorously deterministic, so the rules are:

- No floating point anywhere — integer and permille math throughout
- A small explicit seeded PRNG (xorshift32); never `System.Random` or `UnityEngine.Random`
- No wall-clock or `DateTime` inside the sim
- No iteration over unordered collections where order affects results
- Identical config loaded on both client and server

### Stack

Unity 6 LTS (2D/URP) · Unity Gaming Services — Authentication, Cloud Save, Cloud Code (C# modules),
Leaderboards, Economy · Firebase Cloud Messaging for push · .NET 9 on the server side.

### What M6 delivered — a self-running weekly cycle

- **Weekly modifier rotation** — the four M1 modifiers cycle by week and apply in the resolve
- **Sparks** currency in Cloud Save — +10/day for locking, +2/win; rewards showing up over winning
- **Cosmetic shop** — buy and equip title flair with Sparks; purely visual
- **Weekly reset + Dawn Crown** — the week's #1 is crowned with a dated, ungrindable cosmetic
  (folded into the daily resolve, no extra trigger); standings roll over automatically

### What M5 delivered — a group game

- Player **profiles** (name, accent color, badge), shown in results and standings instead of raw ids
- **Teams**: create/join, one team per player, membership held server-side
- Weekly **standings** — individual and team, computed in the sim from everyone's win/HP totals and
  shown ranked in players' colors (`StandingsCalculator`, unit-tested)
- **Auto-repeat**: a player who skips a day still fights with their last locked squad
- **Local daily notification** just after the 20:00 UTC resolve — no Firebase, no push server

### What M4 delivered — the game is live

- `DailyResolver` in the sim — the nightly round-robin as a pure, tested function; the Cloud Code
  module only wraps it with IO
- Shared serialization (`SquadDto`/`DayResultDto`), a `GameCalendar` with a 20:00 UTC resolve
  boundary, and a Cloud Save wrapper — all unit-tested
- Server `LockSquad` + `ResolveDay` Cloud Code module: validates and stores locked squads, resolves
  the round-robin cross-player, writes results, and accumulates weekly win totals idempotently
- A **Scheduler trigger** firing `ResolveDay` daily at 20:00 UTC — the game resolves itself
- A home screen that shows your record and rebuilds any battle on-device from the stored
  *(squads, seed)* to play through the replay renderer — no video, a few hundred bytes
- Deferred to M5: pushing weekly totals to the leaderboard board (SDK version pin)

### What M3 delivered

- `SquadDraft` in the sim — the 2×3 draft state and legal-squad rules, unit-tested
- A one-component squad builder (IMGUI): roster, front/back grid placement, tactic picker, and a
  live synergy preview that updates as you build
- Local practice against preset opponents that runs the real sim and plays the result through the
  M2 renderer — the full offline **build → watch → adjust** loop, no server involved

### What M2 delivered

- A procedural replay renderer — colored squares on two facing 2×3 grids, no imported art
- `ReplayPlayer` consumes a `BattleEvent[]` and animates lunges, HP bars, floating damage
  numbers and deaths; it owns no game logic and re-animates whatever the sim decided
- Archetype colors, tag pips, and matchup-tinted damage numbers so a fight reads at a glance
- One-component setup (`ReplayDemo`) that runs a real sim battle locally and plays it, with
  in-scene Replay and 1×/2×/4× speed controls

### What M1 delivered

- `BattleSimulator.Simulate` — the full round-based resolver from the design spec
- The archetype counter triangle, the four synergies with 2/3-copy tiers, and all four tactics
- The complete targeting model: reach filter (melee/ranged) then per-tactic selection, with every
  tiebreak ending in instance index so outcomes are total-ordered and reproducible
- Integer damage pipeline (permille multipliers, min-1 clamp, arcane true damage) and the
  effective-stats order: synergy → Berserk → weekly modifier
- Win by elimination, the 30-round cap resolved on remaining-HP percentage (float-free
  cross-multiplication), and a seeded coin flip so there are never draws
- All four example weekly modifiers (Entrenched, Glass Cannons, Vanguard's Hour, Arcane Surge)
- A pure text formatter that prints a battle blow-by-blow, plus a harness to eyeball it
- Determinism proven in CI: same inputs + seed → byte-identical event log, across every
  tactic × modifier combination

### What M0 delivered

- Unity 6 project with the `Daybreak.Sim` / `Daybreak.Client` assembly split, boundary enforced
- Core sim types: archetypes, tags, tactics, squads with grid validation, the event log format
- A deterministic xorshift32 RNG with reproducible per-battle seed derivation
- The 12-unit starter roster as shared config, loaded identically by client and server
- UGS anonymous authentication
- A deployed Cloud Code C# module that compiles `Daybreak.Sim` and reads the same `units.json`
- 22 EditMode tests, all green

## Running it

Requires Unity 6 LTS and a Unity Gaming Services project.

1. Clone and open the project in Unity — UGS packages resolve automatically.
2. Link the project: `Edit → Project Settings → Services`.
3. Enable **Player Authentication** on the [Unity Cloud dashboard](https://cloud.unity.com).
   Anonymous sign-in needs no identity provider.
4. Deploy the server module: point `Assets/Daybreak.ccmr` at `CloudCode/Daybreak.sln`, then
   `Window → Deployment → Deploy`.
5. Open `Assets/Daybreak/Scenes/Boot.unity` and press Play.

Full setup notes, including the non-obvious bits, are in
[`Assets/Daybreak/Docs/MILESTONE-0.md`](Assets/Daybreak/Docs/MILESTONE-0.md).
The complete design specification lives in
[`Assets/daybreak-game-design-and-build-guide.md`](Assets/daybreak-game-design-and-build-guide.md).
